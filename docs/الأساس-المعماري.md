# وثيقة الأساس — منصّة الأنظمة الموحّدة (Blueprint)

> مسودّة أولى للنقاش بين الشركاء. الهدف: تحويل النظام الداخلي من «نظام لشركة واحدة» إلى **منصّة موحّدة متعددة العملاء** نبني عليها طبقة طبقة.
> الاسم والدومين والشعار مؤقتة لحين التأسيس.

---

## ١) محضر الاجتماع الأول للشركاء

**الحضور:** إبراهيم (النظام الداخلي ERP + منصّة حروف ودروس + الواجهات) · تركي `Turky305yt@gmail.com` (الكانب التقني، قواعد البيانات، الربط، منتجات تقنية).

**القرارات الجوهرية:**

1. تأسيس شركة تقنية تبني **أنظمة ERP مخصّصة للشركات**.
2. الانطلاق من النظام الداخلي الحالي (نسخة إبراهيم سعود) كنواة، بعد فصله في مشروع ودومين مستقلّين (تم).
3. بناء **قاعدة/منصّة موحّدة** بدل أنظمة منفصلة: كود واحد، قاعدة بيانات واحدة، والتحديث ينزل للجميع.
4. **سجل تطبيقات** (Apps): كل ميزة = تطبيق مستقل (مبيعات، فوترة، مهام، مشاريع، رادار محتوى…)، نفعّل لكل عميل ما يحتاجه فقط.
5. **لوحة تحكم مركزية** للشركاء: إدارة العملاء + تفعيل/إيقاف التطبيقات لكل عميل + نشر التحديثات.
6. كل تطبيق مخصّص نبنيه لعميل **يُحفظ في الكتالوج** ليُعاد بيعه لعملاء آخرين → ينمو رصيد التطبيقات.
7. **الميزة التنافسية:** واجهة مستخدم جميلة وسهلة + قابلية التخصيص (White-label).
8. **موقع للشركة** على نفس الدومين، يحتضن النظام الداخلي، ويعرض حروف ودروس كأحد أعمالنا لرفع القيمة السوقية.
9. **المنتجات:** المنصّة نفسها أول منتج نبيعه (B2B تخصيص أنظمة) + حروف ودروس (B2C/B2B).
10. البدء الآن على دومين مؤقت؛ وعند جهوز العقود/التأسيس/الشعار: تغيير الاسم/الإيميلات ونقل/تثبيت قواعد البيانات.

**أول «عميلين» على المنصّة = نحن:**

| العميل (Tenant) | الاستخدام | تطبيقات إضافية يحتاجها |
|---|---|---|
| إبراهيم سعود | إدارة أعمال المحتوى/البودكاست | رادار المحتوى، ضيوف سَعي، المدونة، البرومتات، الهوية البصرية |
| الشركة التقنية | إدارة أعمالنا الداخلية | الأساس فقط (بلا تطبيقات المحتوى) |

## ٢) تقييم النظام الحالي

### نقاط القوة
- **واجهة هوية «Liquid Glass» جذّابة** وتجربة عربية RTL ممتازة — وهي ميزتكم التسويقية، تُبنى عليها.
- **يعمل بلا خادم/بناء** (HTML + JS + Supabase مباشرة) → نشر رخيص وسريع وصيانة بسيطة.
- وحدات أعمال ناضجة فعلاً: CRM/مهام، فوترة، مبيعات، مواعيد، تقويم، **غرفة مشروع** بروابط عملاء وفريلانسرز (RPC آمنة بالتوكن)، مدونة، رادار محتوى، برومتات.
- أمان صفوف (RLS) مُطبّق على الجداول، ودوال `SECURITY DEFINER` لوصول الضيوف بالتوكن.

### القيود (التي يحلّها التحوّل للمنصّة)
- **أحادي العميل وأحادي المستخدم:** كل البيانات تُخزَّن غالباً ككتلة JSON واحدة في جدول `app_state` لمالك واحد، والدخول مقيّد بإيميل مدير واحد (`ADMIN_EMAIL`). لا يوجد مفهوم «عميل/Tenant» ولا فريق.
- **ملف واحد ضخم** (`app/index.html` ~2254 سطر) يجمع كل التطبيقات → صعب أن «نفعّل/نطفّئ» تطبيقاً لعميل، أو نحدّث تطبيقاً دون لمس الباقي.
- **الهوية والتطبيقات «مزروعة» في الكود** لا تأتي من إعدادات العميل → التخصيص يدوي.
- لا توجد طبقة «كتالوج تطبيقات» ولا «أدوار» ولا «لوحة تحكم مركزية».

### الخلاصة
النواة ممتازة كـ **منتج**، لكنها مبنية كـ «تطبيق» لا كـ «منصّة». التحوّل المطلوب = إضافة **طبقة تعدّد العملاء** + **تفكيك التطبيقات إلى وحدات** + **لوحة تحكم مركزية**، مع الحفاظ على الواجهة والوحدات الحالية كما هي قدر الإمكان.

## ٣) المعمارية المستهدفة (المنصّة الموحّدة)

### المفاهيم الأساسية
- **Tenant (عميل/مساحة عمل):** كيان مستقل ببياناته وهويته وتطبيقاته المفعّلة (إبراهيم سعود، الشركة التقنية، وكل عميل قادم).
- **App (تطبيق/وحدة):** ميزة مستقلة قابلة للتفعيل والتحديث منفصلاً (مبيعات، فوترة، مهام…).
- **App Catalog (الكتالوج):** قائمة كل التطبيقات المتاحة للبيع/التفعيل، مع وصف وتصنيف وإصدار.
- **Feature Flags لكل عميل:** أي تطبيقات يراها كل عميل (تُضبط من لوحة التحكم).
- **Roles (الأدوار):** مالك المنصّة (أنت + تركي) · مدير العميل · مستخدم العميل · ضيف/فريلانسر بالتوكن (موجود).

### لوحة التحكم المركزية (Super-Admin)
شاشة للشركاء فقط، فيها:
- قائمة العملاء (تبدأ بـ: إبراهيم سعود، الشركة التقنية) مع حالة كل واحد.
- لكل عميل: ✔︎ على التطبيقات المُفعّلة، إعدادات الهوية (شعار/ألوان/اسم/دومين)، الخطة/الاشتراك.
- نشر التحديثات: تحديث تطبيق في الكتالوج → ينعكس على كل من فعّله.
- إنشاء عميل جديد (Onboarding) في دقائق، وإضافة تطبيق مخصّص ثم حفظه في الكتالوج.

### نموذج البيانات الموحّد (قاعدة واحدة)
نضيف جداول الطبقة الجديدة:

| الجدول | الغرض |
|---|---|
| `tenants` | العملاء: id, name, slug, branding(jsonb), domain, plan, created_at |
| `memberships` | ربط المستخدمين بالعملاء: user_id, tenant_id, role |
| `app_catalog` | كل التطبيقات: app_key, name, description, category, version, is_core |
| `tenant_apps` | تفعيل التطبيقات لكل عميل: tenant_id, app_key, enabled, settings(jsonb), version |

ثم نضيف عمود **`tenant_id`** لكل جداول البيانات (`app_state`, `tasks`, `freelancers`, `project_rooms`, `posts`, `prompts`, `content_ideas`, `pageviews`, `guest_registrations`…)، ونعيد كتابة سياسات **RLS** لتكون: «المستخدم يصل لصفوف العملاء المنتمي إليهم (عبر `memberships`)» بدل «owner = auth.uid()»، مع صلاحية كاملة لمالك المنصّة. بيانات إبراهيم سعود الحالية تُرحَّل تحت Tenant خاص بها.

### معمارية الواجهة
تفكيك الملف الواحد إلى:
- **قشرة (Shell):** دخول + سياق العميل الحالي + Launchpad + الهوية/الثيم.
- **تطبيقات (Modules):** كل تطبيق ملف/مجلد مستقل يُحمّل حسب `tenant_apps` → يتيح تفعيل/إيقاف/تحديث كل تطبيق على حدة.
- الثيم لكل عميل (شعار/ألوان/اسم/دومين) يأتي من `tenants.branding` → التخصيص بضغطة.
(يبقى static في البداية؛ ويمكن لاحقاً نقل الواجهة لإطار أحدث لو احتجنا، دون كسر الفكرة.)

## ٤) خارطة الطريق (طبقة طبقة)

- **المرحلة ٠ (تمّت):** فصل المشروع في مجلد ودومين مستقلّين + قاعدة Supabase جديدة نظيفة + تحييد الهوية.
- **المرحلة ١ — طبقة تعدّد العملاء (DB):** إنشاء `tenants/memberships/app_catalog/tenant_apps` + إضافة `tenant_id` لكل الجداول + تعديل RLS + ترحيل إبراهيم سعود كـ Tenant + إنشاء Tenant للشركة التقنية + تعبئة الكتالوج بالتطبيقات الحالية.
- **المرحلة ٢ — لوحة التحكم المركزية:** شاشة الشركاء لإدارة العملاء وتفعيل التطبيقات، وجعل الـ Launchpad يقرأ التطبيقات المفعّلة من `tenant_apps`.
- **المرحلة ٣ — تفكيك التطبيقات + التخصيص:** فصل كل تطبيق كوحدة مستقلة قابلة للتحديث، وتطبيق الثيم/White-label لكل عميل.
- **المرحلة ٤ — موقع الشركة:** موقع تعريفي على نفس الدومين + عرض حروف ودروس كعمل + المنصّة كأول منتج.
- **المرحلة ٥ — التسويق والتشغيل:** تدفّق إعداد عميل جديد، نموّ كتالوج التطبيقات، والاشتراكات/الفوترة للعملاء.
